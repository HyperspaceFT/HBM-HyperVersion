# Goal 10A isolated crucible, casting and alloy regression

Run `python -B -X utf8 tools/migration/verify_goal10a.py` with the existing Python and JDK 21. The script finds the JDK through `JAVA_HOME`, then `C:\Program Files\Java\jdk-21`, then the `PATH`, and uses the cached Gson 2.10.1 JAR the Goal 3C/4/5B recipe suites use. Each run writes its commands, compiler output and assertions to a distinct `build/migration/goal10a/regression/<id>/result.log`, prints the checks per section and the totals of both worlds, and refuses to run if any stand-in would shadow a production source it compiles. javac receives its file list through an argument file in the run folder. The recipe world writes its config files only to the run's own `scratch-config/hbmRecipes`.

A failed assertion is printed as `AssertionError in <section> ...`; the remaining sections and the second world still run, and the run fails at the end if any section failed. Passed checks are counted, failed ones are not. Other exceptions are printed as `Exception in <section>` with their stack trace and also fail the run.

`python -B -X utf8 tools/migration/goal10a_mutation_check.py` reverts eighteen Goal 10A decisions one at a time in a temporary copy of `src/main/java` under `build/migration/goal10a` and reruns the regression (log: `build/migration/goal10a/mutation_check.log`). The unmutated baseline must pass first. A mutation counts as detected only when the regression reports an `AssertionError`; a mutation that does not compile or only raises another exception is reported as an error. The source tree is hashed before and after; the check fails if it changed. `--source DIR` mutates another source root and `--log FILE` writes elsewhere.

`python -B -X utf8 tools/migration/verify_goal10a_resources.py [--source-only]` checks the scrap textures (through `goal10a_scrap_textures.py --check`), the imported and derived assets against `migration/goal10a-resource-ownership.json` and the original, the JEI background paths, the client `ItemProperties`/`ItemColor` registrations, the recipe-selector call in the crucible screen, the 20 Goal 10A language keys in the provider, `zh_cn.json` (same `%s` count) and `zh_cn-map.json` (deferred 108), and the two removed keys. Full mode also compares the generated output with `build/migration/goal10a/stamp-before-g10a.json`: +5 scraps models, `en_us.json` and `scraps.json` modified, the changed generation inputs, and the scraps model overrides.

Expected numbers come from the original at `608fec4`, not from the NEO classes: `TileEntityCrucible.java:56-69` (two stacks of `MaterialShapes.BLOCK.q(16)` = 10,368 quanta, process time 20,000, diffusion 0.25, max heat 100,000), `:344-406` (heat pull, smelting from 50,000 with `(heat - 50,000) * 0.05`, routing), `:408-434` (alloying every `frequency` ticks), `:455-503` (insertion, `required * 10,368 / total input`: steel 5,760, tungsten 3,456, cobalt 1,152), `:164-224` and `CrucibleUtil.java:51-80` (spouts at the centre +- 1.875, y + 0.25, six blocks down, 24 quanta, safe mode), `CrucibleRecipes.java:91-93` and `:143-196` (`crucible.hss`, the JSON format), `Mats.java:104-141` (IDs, names, colours), `OreDictManager.java:398` (`fragment_cobalt` is `nuggetCobalt`), `ShredderRecipes.java:178`, `TileEntityFoundryBase.java:95-145` and `TileEntityFoundryCastingBase.java:28-106` (mold). NEO choices from the plan (D3 recipe-name validation, the sync layout, JEI data, scraps models) are written out from `migration/GOAL10A.md`.

## Stand-ins

`goal10a_regression/stubs.py`, machine world, starts from `goal5a_casting_regression/stubs.py` and then:

- removes the Goal 5A stand-ins for `CrucibleRecipe`, `CrucibleRecipes` and `IControlReceiver` (compiled for real here);
- adds what `GenericRecipe(s)` need: a `SerializableRecipe` stand-in (abstract handler methods and inert JSON helpers; this world does not test handler registration or JSON), `NtmConfig` (528 and expensive mode off), `RecipesCommon.AStack/ComparableStack`, `MetaHelper.newStack(ItemLike, ...)` and `getMeta`, `I18nUtil`, `BobMathUtil.getShortNumber`, `ItemStackUtil.addTooltipToStack`, `WeightedRandom`, more `ChatFormatting` values;
- replaces `Component`/`MutableComponent` with value objects (key, arguments, literal flag, appended siblings; `equals` by value, so `GenericRecipe.getName`'s `Component.empty()` comparison works), `ItemStack.getDisplayName()` as the translatable item description ID, `Item.getMaxStackSize(ItemStack)`;
- declares the extra items and blocks the tests need (things that must not melt, the crucible and foundry mold blocks) and generates `CastPlateItem.Type` from the production enum so the stand-in META is production's ordinal;
- `NuclearTechMod` gains `MODID`, `withDefaultNamespace` and a `LOGGER` that records warnings;
- `Level`: `manualClock` stops `getGameTime()` from advancing on every call (the Goal 5A behaviour stays the default; the crucible reads the clock twice per tick once a recipe is selected), and `clip()` answers per ray-start column (`floor x, floor z`) so the front and the rear spout can hit different molds in one tick; every `ClipContext` is recorded;
- `Container.stillValidBlockEntity` follows Minecraft's rule that the block entity is still in its level at its position and the player is in reach; reach is a player flag (`inReach`);
- one ordered buffer (the Goal 9B model): every value goes to one typed list with a reader index; `writeObject/readObject` remain for the mold's `ItemStack.OPTIONAL_STREAM_CODEC` stand-in. A read of the wrong type throws `ClassCastException`, which the sync section reports as a failed check;
- `CompoundTagControl` compiles against `CustomPacketPayload`, `StreamCodec`, `FriendlyByteBuf` NBT/position fields, an `IPayloadContext` that runs enqueued work at once and returns the sender, and an `InventoryUtil` that reports no held items;
- a small `mezz.jei` surface (`ISubtypeInterpreter`, `UidContext`, `RecipeType`, `RecipeIngredientRole`, `IRecipeCategory`, `IGuiHelper`, `IDrawableBuilder`, `IDrawable`, `IRecipeLayoutBuilder`, `IRecipeSlotBuilder`, the rich tooltip callback). The fixture's layout builder records every slot, so the categories' `setRecipe` output is read back.

Recipe world: `goal4_recipe_regression/stubs.py` with the Goal 3C `CrucibleRecipes` stand-in removed, `INGOT_DURA_STEEL`/`FRAGMENT_COBALT`/`POWDER_COBALT_TINY` added to `NtmItems` when the shredder table no longer names them, `LOGGER.warn` recording, and `Component.append`.

## Sections

Machine world:

1. Materials: order Copper, Tungsten, Cobalt, Steel, DuraSteel; IDs 2900/7400/2700/30/33; names; light/dark/molten colours; `SMELTABLE`; lookup by ID and name; `hbmmat.<name>` keys; exactly five; unknown IDs/names.
2. Melt table: the 13 entries in order with item, material and quanta; `getMaterial` per item, a fresh stack per call that cannot change the table; the unmodifiable list; plates, powders, wire, ores, cast plates, molds and coal do not melt; scraps of every material, the Goal 5A copper scrap layout, amounts 1 and 10,368 valid, 0/-1/10,369 and unregistered IDs rejected.
3. Heat, smelting and routing: heat pull and decay, the 50,000 threshold, the progress delta, reset without input, one item from the first smeltable slot at 20,000; no recipe: steel, tungsten, cobalt fragment, DuraSteel and copper all to the waste stack; `crucible.hss`: steel, tungsten, cobalt and DuraSteel to the recipe stack; copper in a slot is not smelted while it is selected.
4. Insertion: waste capacity without a recipe; `crucible.hss` refuses copper ingots and scraps; the maxima 5,760/3,456/1,152 at exactly the limit and one quantum over (ingots and cobalt fragments); each input against its own maximum; DuraSteel put back up to the recipe stack's capacity; the recipe stack's total; a full waste stack does not block an input; slot occupancy, shift-click and item intake under `crucible.hss`.
5. Alloying: 40/24/8 -> 72 on game time 18 and not on 10..17; one short of each input; existing output and surplus inputs; nine steps in game times 1..89 and the tenth at 90, each exactly on a multiple of 9; 5 steel + 3 tungsten + 1 cobalt ingot melted from slots become 648 DuraSteel with the quanta conserved every tick.
6. Pouring: rear spout for the waste stack with the ray (start, six blocks down, colliders and fluids); 24 quanta per tick and the last remainder with the entry removed; the recipe stack from the front without a recipe; with `crucible.hss` only DuraSteel pours from the front, steel stays (also into an empty mold) until the recipe is cleared; both spouts in one tick; list order; a mold holding another material; cobalt skipped and kept; no hit, a side face, a non-mold block entity, a mold block without a plate mold; the other three facings.
7. Mold: 216 quanta; copper/steel/tungsten/DuraSteel plates with META 5/11/6/12 after exactly 200 ticks; full mold, uncollected plate, cobalt, an unregistered material, another material, nothing; a partly filled mold does not cool; no plate mold; save and load by material ID including Goal 5A copper, cobalt, unknown and negative IDs and an over-full amount; sync; mold scraps.
8. Recipe selection and permission: `crucible.hss` and `"null"` accepted with both stacks kept; unknown names, other case, other index, missing keys, a numeric selection and a null tag ignored; `hasPermission` (menu open, no menu, another crucible's menu, another level, out of reach, client side); the real `CompoundTagControl.handleServer` with and without permission and with an unknown name.
9. 9b. ## Not covered

- Minecraft itself: real ray collision, entity search areas, chunk loading, the server tick order, packets and payload codecs on a network, data components, registries, model baking and item colours, JEI's runtime (display, focus, click areas, subtype use), the recipe selector screen, the crucible screen, tooltips, sounds, dedicated servers and gameplay.
- `MachineCrucibleBlock`/`FoundryMoldBlock` interactions (shovel, break, mold insertion by hand, look overlays) and hopper transfers; the placement rules they use are compiled.
- Original behaviours the plan leaves out (D6, D9, D10): other crucible recipes, plates/powders/ores in the crucible, contact damage, soot, molten metal rendering and other casting devices.
- `SerializableRecipe.readRecipeFile` leaves its `FileReader` open; on Windows the enabled `hbmCrucible.json` therefore cannot be deleted while the JVM runs, so section 5b restores the defaults through the handler instead of deleting the file (pre-existing behaviour, not a Goal 10A change).
