# Goal20C isolated verification

Two verifiers cover the Goal20C spent fuel batch: the machine (the spent fuel pool drum, the fuel pool table with its strict and lenient readers and client sync) with an exact cooling-time model for the finite ledger, and the recipes and resources (the six empty breeding rod recipes, the nine depleted rod → hot waste recipes, the drum recipe, the waste registrations and depleted rod craft remainders, the hazard registrations, the thirteen language keys, the nine imported assets, the provider and registration edits, the default fuel pool rows, the custom fuel pool example and the generated files). Unlike the earlier batches they do not reuse an older isolated world: the machine run compiles three production classes over a small stand-in world of its own. Run them from the NEO repository with the existing Python 3 and JDK 21; they need no Gradle, game, server or network:

- `python -B -X utf8 tools/migration/verify_goal20c_machine.py [--mutations]`
- `python -B -X utf8 tools/migration/verify_goal20c_recipes.py [--mutations]`

Always pass `-B`. Without it, the imports leave `__pycache__` bytecode caches in `tools/migration/goal18a_regression`, `goal20b_regression` and this directory.

Outputs go to unique directories under `build/migration/goal20c/<machine|recipes>/`. Each report records the exact commands and exit codes, the SHA-256 of the production sources, fixtures, stubs, adapters and JDK binaries, the original HEAD and the original file hashes, and `source_stable_after_run` (sources hashed again after the run). A mutation counts only after its temporary copy compiles (where compiled) and the run then fails with the expected `AssertionError` fragment. Both verifiers compare against the frozen Goal20C start under `build/migration/goal20c/baseline-files` and the hashes in `build/migration/goal20c/baseline.json`.

**The drum only ever runs inside the stub world.** Compilation and isolated services never prove game, save, GUI, JEI, rendering, multiplayer or dedicated-server acceptance; the real-engine tick evidence for the cooling is the Goal20C GameTests.

## Machine

`verify_goal20c_machine.py` first freezes the drum statically (`machine_static.py`) against the original `TileEntityWasteDrum`, `WasteDrum`, `ContainerWasteDrum`, `GUIWasteDrum`, `FuelPoolRecipes` and `ModBlocks.java:2276` (d31426c): `DECAY_TICKS` 72000 = 60 × 60 × 20 with its javadoc citing the original formula at `:206`, `r = DECAY_TICKS / water`, a roll for every non-empty slot, water as `WATER`/`FLOWING_WATER` fluid states at loaded neighbours over all six directions, `setChanged` only after a replacement, 12 slots with stack limit 1 on every face, automation insertion only into empty slots that accept a table key (`canPlaceItemThroughFace` = `getItem(slot).isEmpty() && canPlaceItem(slot, stack)`, a NEO-only guard because a vanilla hopper stacked 14 into slot 0), the extraction rule on the slot content, no radiation, sound or particle calls in the block entity, the menu slot coordinates with the player inventory at y 107, the 176 × 189 screen with its info panel, block strength 5/10 with `requiresCorrectToolForDrops()` (original `Material.iron` requires a tool), bubbles that skip the neighbour below in a `@OnlyIn(Dist.CLIENT)` `animateTick`, the strict sync reader and lenient config-file path (`readRecipeStream` encodes the canonical snapshot of the replacement rows with `encodeSnapshot(writeRows(replacement))` before replacing the table and throws `invalid(...)` when it is too large or cannot be written; `writeSnapshot` = `writeRows(RECIPES)` plus the strict `readSnapshot` self-check), the `SerializableRecipe` import and handler line for `FuelPoolRecipes`, and the client-only boundaries (the packet reaches `FuelPoolRecipeClientSync` only from its client handler, the screen only from the client entry point).

It then compiles the production `FuelPoolRecipes`, `FuelPoolRecipeClientSync` and `MachineWasteDrumBlockEntity` beside `com/hbm/blockentity/machine/Goal20CMachineRegression.java` over the stand-ins of `machine_stubs.py`:
- `Item`/`ItemStack` with a META patch beside the item default (`DepletedFuelItem` defaults to META 0; setting the default removes the patch like `PatchedDataComponentMap.set`), `MetaHelper`, a defaulted item registry holding every production `NtmItems` id, the vanilla `ResourceLocation.parse` rules;
- `SerializableRecipe` with the real Gson and the production `readRecipeStream`/`readRecipeLenient` bodies copied verbatim at run time;
- `MachineBaseBlockEntity`, `Level` (client flag, replaceable random, declared unloaded positions, a fluid map that records reads of unloaded positions), `Direction` in the vanilla order, `BlockPos`, `Fluids`, and inert menu, component and annotation holders.

The fixture covers: the nine default rows in the original order; the strict reader (unknown and invalid ids, input count 0/2, the 32767 wildcard, negative METAs, output counts 0/65, four-element arrays, air and the `nothing` placeholder, non-integer and out-of-range numbers, a duplicate key, missing tables, 4097 rows, over 256 KiB, a lone surrogate); the lenient config-file path (five bad rows skipped and logged, whole-file failures leave the table unchanged, a compact 4096-row file under 256 KiB raw whose canonical snapshot exceeds 256 KiB is rejected with the table unchanged while a 1,000-row compact file is accepted, an empty table accepts nothing, `migration/goal20c-custom-fuelpool-example.json` loads ten rows); the snapshot round trip; the client sync (defaults before a packet, an invalid snapshot kept out, an empty snapshot authoritative, logout); the slot rules on every face (automation refuses every filled slot, hot, cool or foreign, and still fills the empty one); water counting; the decay loop with a scripted random (no water for 20,000 ticks, the bound `72000 / w` for 1–6 water, one roll per filled slot, cool waste rolling without change, client no-op, one `setChanged` per cooling tick, output count clamped to 1, the level random versus `setDecayRandom`); and a seeded Monte Carlo (16 drums of 12 hot items per water count) compared with the exact model.

`finite_model.py` writes `finite-model.json`: per water count 0–6 the per-tick probability `1/r`, the expected, median and 95 % cooling time of one slot (geometric, mean `r`), and the exact expected time for a full drum of 12 (the expected maximum of 12 geometric times, cross-checked by direct summation), plus the ledger of 24 depleted rods → 48 hot waste + 24 empty ZIRNOX rods in 4 drums. The run adds the Monte Carlo agreement (within 5 standard errors) to the same file.

`--mutations` applies 24 compiled edits (decay 36000, roll only key slots, water without DOWN, flowing water excluded, unloaded neighbours read, extraction allowed for hot waste or read from the passed stack, stack limit 2, `setChanged` every tick, client-side decay, unclamped output count, the client asking the server table, a dropped or reordered default row, lenient made strict and strict made lenient, wildcard, input count 2, duplicates and four-element rows accepted, a META patch on plain outputs, an empty client table falling back to the defaults, automation stacking into a filled slot, the canonical snapshot guard removed) and 20 static edits (decay 36000, a key filter before the roll, chunk radiation, a sound, a client import, screen height 166, a moved info panel, a moved slot, player inventory y 84, resistance 6, bubbles below, `animateTick` without `@OnlyIn`, a client call outside the client handler, a lenient sync reader, the automation empty-slot guard removed, the `:206` javadoc citation changed, `requiresCorrectToolForDrops()` removed, the canonical snapshot guard removed, the handler line dropped, the `writeSnapshot` self-check removed).

## Recipes and resources

`verify_goal20c_recipes.py` is static (`recipe_static.py`); it reads, without execution:
- the provider statements for the six empty breeding rod recipes and the drum against the original `RodRecipes.java:50-55` and `CraftingManager.java:287` (the steel/lead plate and lead ingot ore entries map to the NEO items), and the nine `addWasteRecipe` calls with `MetaHelper.newStack(waste, 2, 1)` against `RodRecipes.java:39-47`;
- `NtmItems`: the nine `waste_*` registrations with `DepletedFuelItem` and the nine depleted rods with `craftRemainder(ROD_ZIRNOX_EMPTY)` and unchanged ids (original `setContainerItem`, `ModItems.java:2972-2980`), nothing else changed; `DepletedFuelItem` (META 0 default, both states listed, the hot-only gold tooltip, `isHot` as META > COOL, `getEntityLifespan` returning `Integer.MAX_VALUE` so the dropped item never reaches its despawn age, `createEntity` calling `setInvulnerable(true)` and `setPickUpDelay(10)` on the vanilla entity and returning null, and no `setUnlimitedLifetime`) and the `0xFFBFA5` hot tint;
- `HazardRegistry`: the nine `registerOtherWaste` multipliers against `:255-263`, the body (cool `base * 0.075`, hot `base` plus `HOT 5`) against `:629-636`, the six plain registrations against `:208-217`, the shared constants, every pre-existing line unchanged;
- every other edited registration and provider file differing from its frozen copy by insertions only, with the expected lines; `CommonEvents` unchanged;
- the thirteen language keys in `NtmLanguageProvider`, `zh_cn.json` and `zh_cn-map.json` (11 upstream against the original `en_US.lang`/`zh_CN.lang` lines; 2 local: `item.hbmsntm.waste_zfb_mox` with a local Chinese and `desc.gui.wasteDrum.info` from `GUIWasteDrum.java:31-33`), each file changed only by these keys, and the totals (en 2,357, zh 2,249, map 2,357, deferred 108);
- the nine asset copies byte-identical to the originals, and the six item textures equal to the original `setTextureName` targets;
- the default fuel pool rows against `FuelPoolRecipes.java:27-35`, and the custom example against the production row grammar (rows 1–9 the defaults, row 10 the billet illustration);
- the generated files read at run time: the 16 recipes and their advancements, the drum blockstate, `cube_column` block model and item model, the nine waste item models (natural uranium, U233 and U235 on `item/waste_uranium`), the loot table, the pickaxe tag and the thirteen English keys; the generated tree gains exactly these 45 files and, of the files present at the Goal20C start, only `en_us.json`, the pickaxe tag and the migration stamp change. A missing generated file fails the run with a clear message after every other check (rerun after `runData`).

Mutations (`--mutations`, 33 static copies): hazard cool factor 0.1, HOT 4, multiplier 12, `nuclear_waste` on the billet amount, a changed pre-existing hazard line; waste recipe count 1, META 0 and a swapped rod; the drum pattern; empty rod count 8; a removed craft remainder, a changed rod id, a waste item without `DepletedFuelItem`; the tint; a non-insert provider edit; a removed Chinese key, a mapping kind, a provider English text, a lost info line break; a corrupted GUI texture; `setInvulnerable` removed, `setUnlimitedLifetime` reintroduced, the `getEntityLifespan` override removed, `isHot` as `== HOT`, and the drum registration without `requiresCorrectToolForDrops()`; a dropped default row; a duplicate and a wildcard example row; and five generated-file copies.

Not covered: the game, real chunks and fluids, NBT encoding and saves, the GUI, JEI, rendering, the dropped item entity, hazard ticks, crafting in a real recipe manager, multiplayer and the dedicated server.
