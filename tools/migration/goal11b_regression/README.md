# Goal 11B isolated oil refining regression

Run `python -B -X utf8 tools/migration/verify_goal11b.py` with the existing Python and JDK 21. The script finds the JDK through `JAVA_HOME`, then `C:\Program Files\Java\jdk-21`, then the `PATH`. Each run writes its commands, compiler output and assertions to a distinct `build/migration/goal11b/regression/<id>/result.log`, prints the checks per section, and refuses to run if any stand-in would shadow a production source it compiles. javac receives its file lists through argument files in the run folder.

A failed assertion is printed as `AssertionError in <section> ...`; the remaining sections still run, and the run fails at the end if any section failed. Passed checks are counted, failed ones are not. Lines starting with `info:` report observed numbers; they are not asserted and are no gameplay claim. Sections 1j, 5s and 8t are text checks run by `verify_goal11b.py` itself and report the same way. A run on the real production source also copies the recipe exported in section 6 to `build/migration/goal11b/recipe-reference/ass.tank.recipe.json` (written by the production `GenericRecipes.writeRecipe`).

`python -B -X utf8 tools/migration/goal11b_mutation_check.py` reverts or breaks 26 Goal 11B decisions one at a time in a temporary copy of `src/main/java` under `build/migration/goal11b` and reruns the regression (log: `build/migration/goal11b/mutation_check.log`, one folder per run under `build/migration/goal11b/mutation-runs/`). The unmutated baseline must pass first. A mutation counts as detected only when the regression reports an `AssertionError`; a mutation that does not compile or only raises another exception is reported as an error, and an exception next to a detection is logged as `also crashed`. The language provider is mutated as text and the generated JSON is not regenerated, so that mutation is caught by the provider-text check of section 8t. The source tree is hashed before and after; the check fails if it changed. `--source DIR` mutates another source root and `--log FILE` writes elsewhere.

`python -B -X utf8 tools/migration/verify_goal11b_resources.py [--source-only]` checks the generated tree against `build/migration/goal11b/stamp-before-g11b.json` (3850 files before and after: exactly `en_us.json` modified, nothing added or removed), that the current stamp's generation inputs match the sources and differ from the pre-Goal 11B stamp in exactly the 8 Goal 11B inputs (7 Java sources and `zh_cn.json`), that the English and Chinese deltas are exactly `overlay.repair_with` = `Repair with:` / `修理材料：` (2116 and 2008 keys; the pre-Goal 11B bytes are read from the Goal 11A release JAR after checking its SHA-256), and the `zh_cn-map.json` entry (local translation). Full mode also compares the built JAR's entries with the generated files, `zh_cn.json` and the classes of the 7 Java sources, and writes `build/migration/goal11b/generated-check.json` for `package_goal11b.py`, which keeps the JAR as `build/migration/releases/goal11b/hbmsntm-198A-goal11b.jar` with `SHA256SUMS.txt` and `release.json`, explains every entry of the delta to the Goal 11A release and checks the recorded hashes of the 11A, 10C, 10B, 10A, 9B, 9A and 8 releases. After Goal 11C (`migration/GOAL11C.md`) `verify_goal11b_resources.py` runs its unchanged checks against the post-Goal 11B state (the pre-Goal 11C stamp `build/migration/goal11c/stamp-before-g11c.json`, the Goal 11B release JAR, and the git-free snapshot `build/migration/goal11c/base-g11b/` for the inputs and the map Goal 11C changes; for `AssemblyMachineRecipes.class`, which Goal 11C changes again, the release class must lack the Goal 11C literal `ass.chemplant` that the current build's class holds), then `goal11c_delta()` from `verify_goal11c_resources.py` checks that post-Goal 11B -> now is exactly the Goal 11C set (3 more checks). Goal 11D (`build/migration/goal11d/production.diff`) changes one further generation input, `SerializableRecipe.java`, which Goal 11B and 11C left as it was: `verify_goal11b_resources.py` reads that input as committed at `1e29ad29` (`post_goal11c_bytes()` from `verify_goal11d_resources.py`), and `goal11d_delta()` from that module checks that post-Goal 11C -> now is exactly the Goal 11D set (3 more checks).

## Stand-ins

`goal11b_regression/stubs.py` starts from the Goal 11A machine world (`goal11a_regression/stubs.py`) and adds:

- production `IPersistentNBT` and `CompatExternal` instead of the earlier stand-ins, and a `LootParams` model (a builder carrying a server level and the origin, as Minecraft's block loot parameters) so the production `getDropsFromLootParams` runs from `MachineRefineryBlock.getDrops`;

- `Level.updateNeighbourForOutputSignal` as Minecraft 1.21.1's (`Level.java:1124-1139` in the NeoForge sources): each of the six neighbours of the given position receives `onNeighborChange` from it; the stand-in records every (neighbour, source) pair. A comparator only reacts to a neighbour on its own Y, so section 9 counts a connection point as reached when a notified source on its Y reads the tank's value;
- `Component` with appended siblings and a style (`fullText()`), `Block.getName`/`hasAnalogOutputSignal`/`getAnalogOutputSignal`, `CompoundTag.isEmpty`/`getAllKeys`, `BlockPos.containing` and `BlockPos(BlockPos)`, `Tuple.Quintet`, `AABB.move`, `Level.getEntitiesOfClass` (no entities), `FT_Corrosive` and `FluidTraitSimple`, `FluidType.onFluidRelease` (recorded), `HbmPlayerAttachments.getData`, `ExplosionVNT.makeAmat`;
- registry entries for the refinery and tank block entity types, the two menus, `BlowtorchItem`, `NtmItems.NOTHING` (the former repair material, so the mutation back to it compiles) and the client proxy's `me()`.

The Goal 11A fixtures `Goal11ABlockAccess` (placement like the server branch of `DummyableBlock.setPlacedBy`: core state, the production `fillSpace`, then each part's block entity from the production `newBlockEntity`) and `Goal11AWorldGen` (the production `spawnOil` for the chain's oil bubble) are compiled unchanged. Placement skips the item handling, `checkSpace` and `checkRequirement`. Section 3 breaks the refinery through `BlockState.getDrops` (the stand-in bridge to the block's protected `getDrops`; the stand-in `Block.getDrops` default drops nothing, the loot tables are not modelled) and restores a dropped item with `IPersistentNBT.restoreData` directly, not through the block's `setPlacedBy`. Not modelled: rendering, sounds, menus and screens, real chunk loading and unloading (section 7 calls `onChunkUnloaded` directly), entities (the tank's ladder and the refinery's fire), explosions beyond the boiler's recorded `ExplosionVNT`.
