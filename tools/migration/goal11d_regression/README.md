# Goal 11D isolated recipe template fluid name regression

Run `python -B -X utf8 tools/migration/verify_goal11d.py` with the existing Python and JDK 21. The script finds the JDK through `JAVA_HOME`, then `C:\Program Files\Java\jdk-21`, then the `PATH`, and reads git (`1e29ad29`, the delivered post-Goal 11C commit). Each run writes its commands, compiler output and assertions to a distinct `build/migration/goal11d/regression/<id>/result.log`, prints the checks per section, and refuses to run if any stand-in would shadow a production source it compiles. javac receives its file lists through argument files in the run folder.

A failed assertion is printed as `AssertionError in <section> ...`; the remaining sections still run, and the run fails at the end if any section failed. Passed checks are counted, failed ones are not. Lines starting with `info:` report observed numbers; they are not asserted and are no gameplay claim. Sections 1t, 3t, 4 and 5 are run by `verify_goal11d.py` itself and report the same way. A run on the real production source also copies the recipe exported in section 1r to `build/migration/goal11d/recipe-reference/chem.polymer.recipe.json` (written by the production `GenericRecipes.writeRecipe`, in the format of the Goal 11C reference); `migration/goal11c-chem-polymer.recipe.json` is a byte copy of it since Goal 11D (the delivered Goal 11C copy, which names `hbmfluid.petroleum`, stays in git at `1e29ad29`).

`python -B -X utf8 tools/migration/goal11d_mutation_check.py` reverts the one Goal 11D decision (`SerializableRecipe.java:389` back to `getUnlocalizedName()`) in a temporary copy of `src/main/java` under `build/migration/goal11d` and reruns the regression (log: `build/migration/goal11d/mutation_check.log`, one folder per run under `build/migration/goal11d/mutation-runs/`). The unmutated baseline must pass first. The mutation counts as detected only when the regression reports an `AssertionError`; a mutation that does not compile or only raises another exception is reported as an error. `src/main/java` and `src/main/resources` are hashed before and after; the check fails if they changed. `--source DIR` mutates another source root and `--log FILE` writes elsewhere.

`python -B -X utf8 tools/migration/verify_goal11d_resources.py [--source-only]` checks the generated tree against `build/migration/goal11d/stamp-before-g11d.json` (byte for byte the stamp of `1e29ad29`; 3850 files before and after: nothing modified, added or removed; the generated fingerprint unchanged), that the current stamp's generation inputs match the sources and differ from the pre-Goal 11D stamp in exactly one input, `SerializableRecipe.java`, and that `en_us.json` (2116 keys), `zh_cn.json` (2008 keys) and `zh_cn-map.json` are unchanged against `1e29ad29` and the Goal 11C release JAR (checked against its delivered SHA-256). Full mode also compares the built JAR's entries with the generated files, the language files and the compiled `SerializableRecipe` classes, and with the Goal 11C release (no entry added or removed; of all entries only the `SerializableRecipe` classes differ; the built class names `getInternalName` and no longer `getUnlocalizedName`, the release class the reverse), and writes `build/migration/goal11d/generated-check.json` for `package_goal11d.py`, which keeps the JAR as `build/migration/releases/goal11d/hbmsntm-198A-goal11d.jar` with `SHA256SUMS.txt` and `release.json`, explains every entry of the delta to the Goal 11C release and checks the recorded hashes of the 11C, 11B, 11A, 10C, 10B, 10A, 9B, 9A and 8 releases. Its `goal11d_delta(check)` (post-Goal 11C -> now is exactly the Goal 11D set, 3 checks), `post_goal11c_bytes()` and constants are imported by `verify_goal11c_resources.py`, `verify_goal11b_resources.py`, `verify_goal11a_resources.py` and `verify_goal10c_resources.py`, which read the post-Goal 11C state from them; this module imports none of them.

Expected values come from the original (`Hbm-s-Nuclear-Tech-GIT` at `d7ef2df`), not from the NEO classes: `SerializableRecipe.java:421-428` (`writeFluidStack`: an array of `stack.type.getName()` (`:424`), the amount, and the pressure only when it is not 0 (`:426`)); `FluidType.java:157-159` (`getName()` returns `stringId`, the constructor name, `:61`; the language key is `"hbmfluid." + name.toLowerCase(Locale.US)`, `:63`); `SerializableRecipe.java:400-402` (`readFluidStack` resolves the name with `Fluids.fromName`); `Fluids.java:961` (`nameMapping` is keyed by `getName()`) and `:980-986` (`fromName` gives `NONE` for any other string). Section 3t checks these lines and that the original and NEO `Fluids.java` declare each fluid the four tables name as `NAME = new FluidType("NAME", ...)`, so the internal name is the field name in both. The reader is unchanged by the user's decision (no fallback for language keys).

## Production code under test

Production world: the production `SerializableRecipe`, `GenericRecipes`, `GenericRecipe`, `ChemicalPlantRecipes`, `AssemblyMachineRecipes`, `SolderingRecipes` and `ArcWelderRecipes` (the four tables are every caller of `writeFluidStack`, section 1t), with real Gson 2.10.1 from the Gradle cache. The templates are written by the production `writeTemplateFile` (what `SerializableRecipe.initialize` writes to `config/hbmRecipes/_<file>` when no custom file exists) and read back by the production `readRecipeFile`.

Post-Goal 11C world: the same sources and stand-ins, but `SerializableRecipe.java` from `git show 1e29ad29` (it differs from the production file in line 389 only, section 5); its run writes the four templates with the post-Goal 11C writer. The production world reads them back with the production reader (section 2) and section 4 compares them with the production templates.

Not compiled: the game loader around the tables (`SerializableRecipe.initialize` with a real config directory, recipe sync), the JEI handlers and the machines. No Minecraft start writes a template here; no custom file is loaded in game.

## Stand-ins

`goal11d_regression/stubs.py`: the Goal 11C recipe world (`goal11c_regression/stubs.py`: every fluid the sources name is a `FluidType` whose `getInternalName()` is the `Fluids` field name and whose `getUnlocalizedName()` is `hbmfluid.` + the lower-case name, as the production `FluidType.java:61` and `:157-159`; `Fluids.fromName` matches the internal name exactly and gives `NONE` otherwise, as the production `Fluids.java`), extended for the soldering and arc welder tables: their Goal 3C name-only handler stand-ins are dropped, `DeferredItem<T>` is a stand-in base class of the `NtmItems` references (the soldering table takes `DeferredItem<Item>`), `AStack.matchesRecipe` exists (not exercised) and `MetaHelper.newStack(ItemLike, [int,] Enum)` keeps the ordinal as the meta (production `MetaHelper.java:37-41`). Item metas of stand-in enums are stand-in ordinals; they are the same in both worlds and are not compared with the game. `NtmItems.castPlateWeldedIngredient` is the Goal 3C stand-in (an item per type), identical in both worlds.

## Sections

Java, production world (`com.hbm.inventory.recipes.loader.Goal11DRecipeRegression verify`):

1. Writer (16 checks): `writeFluidStack` writes `["PETROLEUM",1000]` and `["PEROXIDE",1000,5]`, not the language key; for each of the four tables the template holds every registered recipe and every fluid stack is `[internal name, amount]` plus the pressure when it is not 0, in the order of the registered stacks, and the table has stacks to write; the tables include pressurised stacks. Info: 68 chemical plant recipes with 127 fluid stacks, 29 assembly machine recipes with 1, 39 soldering recipes with 20, 42 arc welder recipes with 6.
2. Round trip (12 checks): each template written by the production writer and read back by the production reader gives every recipe its registered fluids (type, amount, pressure); baseline: the post-Goal 11C template read back by the same reader turns every fluid stack into `NONE` (amount and pressure kept). The recipe and stack counts are printed. The soldering read-back holds every recipe twice in a row (printed; see below), compared once.
3. Reader unchanged, no fallback (6 checks): an internal name reads as that fluid (with and without pressure); `hbmfluid.petroleum`, `petroleum` and an unknown name read as `NONE`; `readFluidArray` maps each element the same way.
1r. `chem.polymer` reference (2 checks): the exported recipe names `PETROLEUM`; read back by the production reader it is 1,000 mB petroleum gas.

Python (`verify_goal11d.py`):

- 1t. Every caller covered (3 checks): `writeFluidStack` is called only from `GenericRecipes` (2) and the soldering and arc welder tables (1 each); of the `GenericRecipes` tables only the assembly machine and chemical plant tables have a fluid limit above 0.
- 3t. Reader and name map (11 checks): `readFluidStack` and `readFluidArray` are identical to `1e29ad29` (modulo line ends); NEO `Fluids.fromName` (unchanged) and its map keyed by `getInternalName()`; NEO `FluidType` names; the original lines cited above; each of the 55 table fluids is declared `NAME = new FluidType("NAME", ...)` in NEO and in the original.
- 4. Delta of the export (20 checks): for each table the production and the post-Goal 11C template differ only in fluid name strings, each old value being `hbmfluid.` + the lower-case new internal name, one per written stack; with each key replaced by its name the post-Goal 11C file is byte for byte the new one (order and formatting included).
- 5. Production diff (4 checks): `SerializableRecipe.java` keeps CRLF, differs from `1e29ad29` in exactly line 389 (`getUnlocalizedName()` -> `getInternalName()`, comment and whitespace kept); `git diff` against `1e29ad29` lists no other file under `src/main/java` or `src/main/resources`, and there is no untracked file there.

Observed, not changed (pre-existing, not Goal 11D): NEO `SolderingRecipes.readRecipe` adds the recipe that its `SolderingRecipe` constructor already added to `recipes` (`SolderingRecipes.java:507` and `:572`), so a custom `hbmSoldering.json` registers every recipe twice; the original constructor does not add itself (original `SolderingRecipes.java:353-364`, `:308`).
