# Goal 5A isolated heat and processing regression

Run from the NEO repository with the existing Python and JDK 21:

```powershell
& 'C:\Users\显卡超频和烤机测试\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -B tools/migration/verify_goal5a_processing.py
```

Each run writes its own UUID directory and full compile/execution transcript under `build/migration/goal5a/processing-regression/`. The script compiles the **current, unmodified production** `MachineBaseBlockEntity`, `AbstractHeaterMachineBlockEntity`, `HeaterFireboxBlockEntity`, `MachineFurnaceCombinationBlockEntity`, `CombinationRecipes`, `ModuleBurnTime`, `FluidTank`, both machine menus, `MenuBase`, `SlotNonRetarded`, and `SlotTakeOnly`. It does not run Gradle, a game, or a server. The integrated case ticks a coal-fueled firebox and oven from zero, removes the heat source after partial progress, exhausts residual heat, saves both machines, restores them, and continues to the first complete coke and creosote output. No heat or progress is injected into this case. Other cases check diffusion, fuel timing and remainder, recipe switching, exact capacity and item limits, blocked outputs, NBT and sync, sided access, client tick isolation, and menu routing.

The stand-ins are deliberately limited to surrounding Minecraft/NeoForge services. `Level` provides only an in-memory block entity map and modeled time; `ItemStack` preserves item identity, count, and one component token. `ContainerHelper` copies modeled stacks into an in-memory `CompoundTag`. The menu stand-in models `moveItemStackTo` and slot placement, including its existing-stack merge pass. The test uses production `CombinationRecipes` and `ModuleBurnTime` with minimal stand-in items and tags; the registry and tag data are not the actual game registries. For a narrow item-limit boundary, the fixture models sugar with maximum stack size 16 and separately subclasses the oven to set a container maximum of one. Those are test conditions, not assertions about vanilla sugar's maximum stack size or normal oven configuration.

The production `FluidTank` class runs its actual fill/type, NBT, and buffer methods. Its client rendering dependencies and `FluidLoadingHandler` implementations are inert stand-ins, so actual canister unloading and rendering are outside this check. Fluid IDs and compatibility name lookups use a minimal modeled registry. The buffer and NBT classes are also modeled rather than Minecraft's actual codecs. Passing these assertions supports the production method call chain and its values within that model; it does not establish an actual Minecraft save file, fluid network, client rendering, dedicated-server loading, real-world behavior, or in-game GUI. The normal resource and JAR audits and any authorized gameplay checks remain separate.
