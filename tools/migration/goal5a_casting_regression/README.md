# Goal 5A isolated copper casting regression

Run from the NEO repository using the already installed Python and Java 21:

```powershell
& 'C:\Users\显卡超频和烤机测试\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -B tools/migration/verify_goal5a_casting.py
```

Each run writes a UUID directory and complete compile/execution transcript under `build/migration/goal5a/casting-regression/`. The first stage compiles the current production `MachineBaseBlockEntity`, firebox and burn module, `MaterialShapes`, `NTMMaterial`, `Mats`, `CopperCastingRecipes`, `CopperScrapsItem`, `MachineCrucibleBlockEntity`, `FoundryMoldBlockEntity`, `MachineCrucibleMenu`, `MenuBase`, and slot classes. A separate stage compiles the live `AnvilRecipes`, `AnvilSmithingRecipe`, `AnvilSmithingCastMoldRecipe`, and `InventoryUtil` against the established anvil fixture services. The runner never starts Gradle or Minecraft.

The principal case starts a firebox, crucible, and plate mold cold with six copper ingots. It ticks the real machine methods until two plates are made and extracted, checking all 432 copper quanta across input, crucible, mold, and output on every tick. Other cases check heat diffusion and cooling, the 50,000 TU threshold, progress and capacity reset, bounded pouring, 200-tick mold cooling, held output and refusal cases, intake timing, save/load and network state, scrap extraction and remelting, nine single-item slots, shift routing, sided access, and client tick guards. A targeted slot case invokes the production hopper-facing placement gate with an occupied first slot, then shift-moves copper through slots 1 and 2 and checks that a full nine-slot crucible refuses the remainder. This checks the shared placement rules; it does not simulate an actual hopper. The printed check count includes a repeated per-tick mass invariant; it is not a count of distinct scenarios.

The anvil stage executes both live tier-2 crucible construction routes (vanilla and NEO copper ingots), checking short inputs, tier rejection, exact consumption, and output. It executes the tier-1 reusable cast-mold smithing recipe's matching, output, and `amountConsumed` contract, including an iron variant-0 reference plate for the first mold, repeated molds from one copper reference plate, and invalid item/meta/order cases. It checks that two modeled copper castplates with variant 5 satisfy and execute the existing tier-2 combination oven construction recipe. A static source gate confirms `AnvilMenu` still passes both recipe consumption amounts to `removeItem`; the menu itself is not run in this stage.

The Minecraft/NeoForge environment is modeled. The in-memory `Level` returns controlled `BlockHitResult` values and records the exact `ClipContext` passed by production code. It does **not** execute actual Minecraft ray collision or filter entities by the requested `AABB`; it records that area while returning the fixture's item entities. Item identity, component token, `CUSTOM_DATA`, player inventory, menu merge, block state, registry, NBT, and byte buffer are minimal stand-ins. `NtmItems.castPlate` is a stand-in that returns a modeled cast plate with copper variant `5`; the anvil fixture models that same identity and variant for the existing oven recipe. The actual item registry, data-component codec, rendering, block hand interactions, `AnvilMenu` runtime, dedicated-server loading, and real world are outside this harness. Those surfaces need their separate checks.
