# Goal 5B isolated graphite and carbon-wire regression

Run from the NEO repository with the already installed Java 21, Python, and cached Gson:

```powershell
& 'C:\Users\显卡超频和烤机测试\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -B tools/migration/verify_goal5b.py
```

Every run writes a UUID directory and full compile/run transcript under `build/migration/goal5b/regression/`. The processing stage compiles the current production firebox, combination oven, `CombinationRecipes`, `ModuleBurnTime`, `FluidTank`, `MachineBaseBlockEntity`, press, `PressRecipes`, and all three menus with slot classes. From zero heat and progress, it burns coal in the firebox, makes one coal coke and 100 creosote in the oven, passes **that same coke stack** into the FLAT press to make one graphite ingot, then passes **that same graphite stack** into the WIRE press to make eight carbon wires. It uses a separate press fuel item and ticks the normal acceleration, extension, retraction, and completion paths. Neither heat nor progress is injected in this integrated case.

Additional processing cases check all three coke inputs, stamp mismatch, fuel and input gates, a custom three-input recipe through an actual press completion (three of four inputs become two outputs), exact 56+8 completion versus 57/full refusal without wear or fuel spending, component mismatch, a smaller container limit, last valid uses of actual 32- and 64-durability modeled stamps, a zero-durability stamp, partial-cycle save/resume, interrupted retraction and restart, stored-fuel exhaustion during a partial stroke, no repeated output, and the press menu's current coke-to-fuel quick move. The cold chain also checks exact 400 press burn points spent and one damage on each stamp; the firebox uses its separate burn-tick/TU state. Two synthetic items named like coke and graphite blocks confirm that the item recipes do not match unrelated item identities; they do not stand in for registered block items.

The recipe stage separately compiles and executes the real `SerializableRecipe`, `GenericRecipe(s)`, and `PressRecipes` with cached Gson and a scratch configuration **inside that UUID output**. It confirms the disabled `_hbmPress.json` template, exactly four new default objects, wildcard input metadata `32767`, direct `PressRecipes.writeRecipe` export to `goal5b-press-defaults.json`, byte-identical enabled custom file replacement, custom count/output, repeat initialization, and received-stream priority/restoration. The exported JSON is suitable for review as a migration reference; its object order follows the production `HashMap` and is not promised stable.

Minecraft/NeoForge registries, items, components, world, sound, menu merge, NBT, buffers, and `StampItem` are modeled services. Production machine and recipe methods execute, but this is not an in-game craft, real registry/datapack load, client rendering, full multiplayer synchronization, or a real disk world save. The production `FluidTank` class runs with inert fluid-loader and renderer dependencies; real container unloading is outside this surface. The processing stage uses a minimal `SerializableRecipe` declaration to compile `PressRecipes`; the second stage is the one that runs the actual loader and Gson. Component-sensitive output assertions use a single modeled component token, not Minecraft's full data-component codec.
